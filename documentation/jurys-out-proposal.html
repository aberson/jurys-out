jurys-out

Codifying judge panels for agentic review workflows, because the jury is still out.

Plan source of truth: ../plan.md · Proposal view: documentation/jurys-out-proposal.html

What I heard

You want a public, thin tool for deciding whether development-review panels deserve their size and cost. The tool must make judges visible to users, resist redundant shared failure, avoid treating roles as a rigid MECE taxonomy, and include enough benchmark execution to establish whether a panel is better than its best individual judge.

Why this shape

The design is a local CLI rather than a service: it keeps diffs, CI evidence, keys, and raw judge output on the operator's machine. It adds a real runner because configurations alone cannot answer the five-judges question, then keeps the runner small: frozen local suites, foreground calls, exact resume, direct OpenAI and Anthropic adapters, and deterministic reporting.

Operator choices

P1

Public project and locked tagline

Public utility. The tag line is locked as supplied.

P2

Transparent panel management for development review

Users see judge roles, rubric, evidence requirements, votes, dissent, abstentions, configuration, and limitations.

P3

A minimal benchmark runner is in version 1

Panel size remains a benchmark hypothesis, not a fixed five-judge product rule.

P4

Local CLI first

No web product is required for the first release.

P5

One focused benchmark-case shape

Task/specification, diff, relevant test or CI evidence, candidate finding, and human adjudication define the initial instrument.

P6

Not rigid MECE

Judge cards declare primary ownership and intentional overlap. The tool measures redundant errors rather than enforcing arbitrary disjoint labels.

Agent defaults

D1

Python/uv/TOML/JSONL local stack

What: Python >=3.12, uv, hatchling, argparse, TOML cards, JSONL data.

Why: Thin, inspectable, and aligned with local benchmarking conventions.

Tweak: Replace any individual component without changing the local-CLI boundary.

D2

OpenAI and Anthropic first

What: Narrow direct adapters to Responses and Messages APIs.

Why: Cross-family comparison is useful while a two-adapter scope stays small.

Tweak: Start with only one adapter, or substitute a provider before build.

D3

Raw outputs stay local

What: Retain raw provider responses by default under Git-ignored run artifacts; public reports expose structured evidence and concise rationale.

Why: Enables audit and parser diagnosis without accidental disclosure.

Tweak: Make raw retention opt-in or remove it entirely.

D4

Foreground append-only execution

What: One case-by-judge call at a time, durable events, and resume only for exact frozen input hashes.

Why: Reproducibility without queues or workers.

Tweak: Permit bounded local concurrency after an evidence-backed follow-up.

D5

Majority with escalation

What: Required members must complete; strict majority decides; ties and no-vote outcomes escalate.

Why: An auditable baseline that preserves dissent.

Tweak: Use weighted, unanimous, or specialist-veto aggregation after comparing it on a frozen holdout.

D6

Hard request/token limits, optional price estimates

What: Request, input-byte, and output-token ceilings always bind; USD estimates require a local versioned price sheet.

Why: Prevents surprise spend without claiming stale pricing is exact.

Tweak: Require a price sheet for every live run.

D7

Calibration and insufficient-data guardrails

What: Good/garbage anchors, frozen holdout cases, recurring sentinels, and explicit insufficient-data results.

Why: A panel-selection claim needs evidence, not a decorative score.

Tweak: Start with an exploratory-only mode that suppresses selection comparisons.

D8

Seven build slices plus two manual live gates

What: Worktree-isolated automated steps, deep review for persistence/provider seams, then bounded live smokes and seed benchmark review.

Why: Tests cover mocks; real provider contracts need separate observation.

Tweak: Merge or split the build slices before repo-sync.

D9–D13 were accepted unchanged and are now part of the canonical plan.

D9

MIT public license

What: Publish under the MIT license.

Why: It is short and permissive for a thin public utility.

Tweak: Change to Apache-2.0 later if an explicit patent grant becomes important.

D10

Concrete spend controls

What: Require a versioned local TOML price book for estimated-USD limits; cap M1 at $1 and M2 at $5.

Why: Request and token ceilings are safe, but a budget needs a reproducible estimate contract.

Tweak: Change the price-book policy or caps in a later plan revision.

D11

Explicit evaluation splits and invariance fixtures

What: Give every benchmark case a calibration, holdout, or sentinel split; test order swaps, identifier renaming, and misleading comments.

Why: This makes the claimed guardrails executable rather than aspirational.

Tweak: Narrow or expand the invariance set in a later plan revision.

D12

Bounded retry policy

What: Retry timeout, connection, HTTP 429, and 5xx failures at most twice, respecting Retry-After and recording every attempt; do not retry auth, validation, refusal, or other 4xx failures.

Why: It is deterministic, auditable, and avoids multiplying bad requests.

Tweak: Change the retry count or narrow the retryable classes in a later plan revision.

D13

Python 3.12-compatible UUIDv4 run IDs

What: Keep Python >=3.12 and use a standard-library UUIDv4 run suffix.

Why: It resolves the UUIDv7 standard-library compatibility mismatch without raising the runtime floor.

Tweak: Require Python >=3.14 and switch to UUIDv7 in a later plan revision.

Not in version 1

  • Web UI or hosted multi-user service
  • Background jobs, queue, scheduler, or distributed execution
  • CI merge gating
  • Automatic panel optimization
  • External dataset scraping
  • Broad provider plug-in ecosystem
  • Opaque debate or hidden chain-of-thought display
  • Database or network listener

Risks to keep visible

Small samples can lie

The first suite cannot establish a broadly superior panel. The report must say insufficient data instead of presenting zero correlation or a winner.

Code-review artifacts can be sensitive or adversarial

Keep raw material local, never log keys, and treat diffs and CI text as untrusted evidence rather than instructions.

Provider output is not a uniform substrate

Schema response, refusal, usage, and pricing behavior differ. Preserve provider-specific facts and fail a required-member run openly.
